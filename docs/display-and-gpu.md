# ros2arm の表示方式と GPU 直結

`ros2arm` の画面の出し方（noVNC / 通常の VNC）と、描画が重いときの選択肢（GPU 直結）をまとめる。
構成全体は [arm-sim-architecture.md](arm-sim-architecture.md) を参照。

> 以下の「速い・遅い」は一般的な傾向で、このリポジトリでは未計測。

## 1. 現状

- 仮想 VNC ディスプレイ + noVNC（`127.0.0.1:6080`）で表示している。
- Gazebo / RViz2 の 3D 描画は **CPU（llvmpipe、ソフトウェア OpenGL）**。重さの主因はこれで、
  表示プロトコルより支配的な見込み。
- そのため README ではデモを 1 度に 1 つだけ起動する運用にしている。

## 2. noVNC と通常の VNC

noVNC は「ブラウザで動く VNC クライアント + websockify（WebSocket ⇄ TCP 変換）」。
裏のサーバーは同じ VNC なので、比較は **ブラウザ経由 vs ネイティブクライアント経由**。

| 観点 | noVNC | 通常の VNC（ネイティブクライアント） |
|---|---|---|
| クライアント導入 | 不要（ブラウザのみ） | 必要（TigerVNC Viewer、macOS 画面共有など） |
| 公開ポート | 1 本（HTTP/WebSocket） | VNC ポート（5900 系）が増える |
| 遅延・画質 | 変換と JS デコードの分だけ劣る | 低遅延・高画質。エンコーディングを選べる |
| クリップボード・キー入力 | 日本語入力や修飾キーに癖が出やすい | 安定 |
| 認証・攻撃面 | ブラウザ経由で、他サイトの Web ページから `127.0.0.1:6080` に接続を試みられる | ブラウザ経由の経路はない（ローカルプロセスからは届く） |
| 暗号化 | HTTP/WebSocket なので TLS 終端を載せやすい | 既定は無暗号。LAN 外なら SSH トンネルが必須 |
| 手順の統一 | 全 OS で同じ | OS ごとに分かれる |

**判断**

- 学習・デモ、誰でも URL で入れたい → noVNC
- 自分専用で快適に使いたい → 通常の VNC（`127.0.0.1` 限定）
- どちらでも CPU 描画の重さは残る。根本対策は次節の GPU 直結

noVNC と通常の VNC は両対応している（compose で `127.0.0.1` 限定の VNC ポートを公開し、noVNC も残している）。

## 3. GPU 直結（X11 共有 + `--gpus all`）

コンテナの GL 描画を GPU に回し、画面は別経路で出す構成。

### 3.1 構成の要点

1. **GPU をコンテナに渡す**: NVIDIA Container Toolkit を入れ、compose で
   `deploy.resources.reservations.devices`（`driver: nvidia`）を指定する（`--gpus all` 相当）。
2. **GL を GPU で動かす**: `NVIDIA_DRIVER_CAPABILITIES=all`（graphics を含める）。
   ホスト側のドライバのライブラリがコンテナに注入される。
3. **画面の出し方**
   - **X11 共有**: `/tmp/.X11-unix` をマウントし `DISPLAY` を渡す。ホストの画面に直接ウィンドウが出る。最も軽い。
   - **Wayland 共有**: ソケットを渡す方式。Gazebo / RViz2 は Qt で動くが、環境差が出やすい。
4. **リモートで使うなら**: X11 共有は「ホストの画面で見る」前提になる。離れた場所から使うには、
   GPU 対応の配信（Sunshine / Moonlight、NICE DCV、noVNC + VirtualGL など）が別途要る。

### 3.2 前提条件

| 項目 | 内容 |
|---|---|
| ホスト OS | **Linux 必須**。macOS 上の Docker VM（Colima 等）は GPU パススルーがないため不可 |
| GPU | NVIDIA が事実上前提。AMD / Intel は `--device /dev/dri` + Mesa の別方式 |
| ドライバ | ホストに NVIDIA ドライバ + Container Toolkit |
| ディスプレイ | ホストに X サーバーが必要。ヘッドレスなら仮想 X を別途用意 |
| アーキテクチャ | NVIDIA 構成は amd64 前提。現行イメージの動作確認は arm64（macOS 上の Colima）のみ |

**macOS + Colima 構成では実現できない。** Linux + NVIDIA のホストを用意する場合の話。

### 3.3 メリット

- Gazebo / RViz2 の描画が実用速度になる見込み。
- カメラ・LiDAR など GPU を使うセンサのシミュレーションが現実的になる。
- ROS 2 のコードは変えずに動く（描画経路だけの違い）。

### 3.4 デメリット・注意点

- **セキュリティ**: X11 共有では、コンテナ内のプロセスがホストの全ウィンドウのキー入力を覗ける。
  `xhost +` は使わない。使うなら `xauth` の cookie を限定して渡す。現在の「隔離」方針とは相反する。
- **再現性**: ホストのドライバ版とコンテナの GL ライブラリの整合に依存し、環境差の問題が出る。
- **VNC / noVNC との併用が難しい**: ホストの GPU 描画を VNC に載せるには VirtualGL 等が要り、構成が複雑になる。
- **ARM 非対応**: 上表のとおり amd64 前提。

## 4. 選択肢の比較

| 案 | 手間 | 効果 |
|---|---|---|
| 現状維持（CPU 描画、デモは 1 つずつ） | なし | 遅いが動く |
| Colima の CPU / メモリを増やす | 小 | CPU 描画が多少改善 |
| Linux + NVIDIA マシンで X11 共有 | 中〜大 | 描画は快適。隔離方針が弱まる |
| クラウド GPU（Linux VM）に置き、Sunshine 等で配信 | 大 | 手元の PC から快適に使える。費用が出る |

重さが実用上の問題になるまでは、現状維持（デモを 1 つずつ起動）で足りる。
問題になった時点で、Linux GPU ホストを用意するかを決める。
