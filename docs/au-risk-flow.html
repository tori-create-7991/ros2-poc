AU-1〜3 通信フローとリスク

対象: このリポジトリの Docker 構成から ros2real (実機) を除いた部分。ros2lab-a / ros2lab-b / ros2arm (シミュ) と、外から接続してくる低信頼コンテナ。

AU-1〜3 とは (PoC1 検証項目詳細 v0.4): DDS-Security の「認証」3項目です。 AU-1 = 未認証参加者が入れるか / AU-2 = 資格情報の一意性・管理 / AU-3 = 不正証明書を弾くか。

1. 現在の構成と通信フロー

赤い矢印・枠がリスク箇所。ros2lab-a/b と ros2arm は同じ ROS_DOMAIN_ID=42 で互いに見える。現在は SROS2 未適用 (ros-jazzy-sros2 は同梱のみ) のため、認証・暗号化・権限制御はない。

2. 通信フロー

#通信中身現状
①低信頼コンテナ → ros2lab-a/bDiscovery (UDP マルチキャスト) → Pub/Sub認証なし lab に繋がれば誰でも参加できる
②ros2lab-a ↔ ros2lab-bトピックの発行・購読無認証・平文
③ros2lab-a/b ↔ ros2armMoveIt への指令 / /joint_states / /tf無認証・平文 シミュなので物理被害はない
④全コンテナ ↔ ./workspaceスクリプト、SROS2 keystore (予定)全員が書き込み可

3. AU-1〜3 のリスクが出る箇所

IDどこで起きるかこの構成での具体例起きると何が困るか
AU-1
未認証参加者の混入
①②③		 lab ネットワークの入口 (①) と、ros2lab-a/b・ros2arm への DDS 参加
  • kali-vnc 等が docker network connect ros2-lab-net で lab に入る (README 記載の手順)
  • SROS2 導入後も ROS_SECURITY_STRATEGY=Permissive や allow_unauthenticated_participants=true が残り、鍵なしの participant が混ざれる
 参加できた時点で、購読 (盗聴) と発行 (指令注入) が可能。例: ros2arm の MoveIt に勝手に軌道指令を送る。認証が破れると他の対策の多くが意味を失う
AU-2
資格情報の一意性・管理
④		 共有 volume ./workspace と、同じイメージから起動する ros2lab-a/b
  • keystore を ./workspace に置くと、全コンテナが秘密鍵を読み書きできる。1つ侵害されれば鍵が盗まれる・差し替えられる
  • ros2lab-a と b が同じ keystore・証明書を使い回すと、1台の鍵で全員になりすませる
  • 証明書の有効期限・CA の設計が未検討 (実質無期限になりがち)
 鍵を1つ抜かれると、そのノード全員 (将来は出荷済み全台) へのなりすましが成立する
AU-3
証明書検証の厳密性
①③		 ros2arm / ros2lab が受け取る参加要求の証明書チェック
  • SROS2 導入後、不正証明書 (期限切れ / 別CA / 自己署名 / 失効済み) で参加を試みる試験の対象
  • 検証が甘いと、偽の証明書で正規ノードになりすませる
  • 失効 (CRL) の確認は Fast DDS 標準プラグインが対応しているか、着手前に要確認
 「認証あり」なのに実際は効いていない状態。書面監査では見つからない。AU-3 はこれを検出するための項目
押さえておく点
  • 今は認証そのものがないので、環境 A (無防備) に当たる。AU-1〜3 はすべて「不合格」が期待値。
  • ros2real を除くと、ros2arm はシミュなので物理被害はない。試験を作り込むには安全な対象。
  • ros2lab-a/b が lab にも default にも繋がっている点は、侵入の足場になる。

4. 試験の進め方 (この構成での例)

  1. 環境 A (現状) で、kali-vnc 相当のコンテナを lab に繋ぎ、ros2lab-a のトピックが見える・購読できることを確認する (AU-1 の「不合格」ベースライン)。
  2. SROS2 の keystore を作り、環境 C (適正設定) を compose で切り替えられるようにする。keystore の置き場は ./workspace 以外を検討する (AU-2)。
  3. 環境 C で、鍵なし participant が拒否されることを確認する (AU-1 合格)。
  4. 環境 B (誤設定: Permissive / allow_unauthenticated / 鍵の使い回し) を作り、各不備を検出できるか確認する。
  5. openssl で不正証明書4種を作り、環境 C で全て拒否されるか確認する (AU-3)。証明書は lab 外に出さない。
