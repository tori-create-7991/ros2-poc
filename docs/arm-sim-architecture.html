アームシミュ構成: Gazebo / MoveIt 2 / RViz2

Factory I/O は Windows 専用のため、Docker 上の ros2arm で代替している。 3 ツールの役割、アーキテクチャ図、サービスブループリントをまとめる。 Markdown 版: arm-sim-architecture.md

動作状況の前提: シミュ（ros2arm）は動作確認済み。実機（ros2real）は ビルド・compose 検証・モックのドライバ起動まで。実機での動作は未確認。

1. 3 つのツールの詳細

Gazebo Harmonic

物理シミュレータ ＝ 世界そのもの

重力・摩擦・接触で物体が動く。ROS 2 とは ros_gz と gz_ros2_control で繋がり、 関節状態を /joint_states として流す。描画は CPU のため重い。

MoveIt 2

動作計画 ＝ アームの頭脳

move_group が Planning Scene（衝突判定）・OMPL（経路探索）・IK・軌道の時間付けを担い、 FollowJointTrajectory で controller に軌道を渡す。

RViz2

可視化 + 操作 UI ＝ 計器盤

MotionPlanning パネルで目標姿勢を指定し Plan / Execute。表示は /joint_states・TF・計画シーンから再構築した像で、 RViz2 自身はロボットを動かさない。

Gazebo は「現実の代わり」、RViz2 は「ロボットの頭の中の表示」。 Gazebo 画面と RViz2 画面は別物。実機に繋ぎ替えても RViz2 側の動きは同じになる。

制御の連鎖（ros2_control）

MoveIt 2 (move_group)
  └─ FollowJointTrajectory ─▶ crane_x7_arm_controller   (JointTrajectoryController)
                                  └─ ros2_control (controller_manager, 200Hz 級)
                                        └─ ハードウェア層  ← ここだけが差し替わる
                                              ・シミュ: Gazebo (gz_ros2_control)
                                              ・実機  : CRANE-X7 ドライバ (Dynamixel, /dev/crane_x7)

ros2lab から送る ros2 topic pub /crane_x7_arm_controller/joint_trajectory は、 MoveIt 2 を経由せず controller に直接軌道を渡す経路。どちらも最後は同じ controller に届く。

Factory I/O との差

観点Factory I/OGazebo + MoveIt 2 + RViz2
得意工場ライン（コンベア・センサ・PLC の I/O）ロボットアームの運動・物理・衝突回避
制御対象PLC のタグ（入出力点）ROS 2 のトピック / アクション（関節角）
動作環境Windows 専用Linux / Mac（Docker + ブラウザ）
失うものPLC 連携（Modbus / OPC UA）、コンベア・ワークの既製部品。補うならコンベア等は Gazebo のモデル / プラグインで自作、PLC 連携は OpenPLC や ROS 2 ブリッジを別途検討（未実装・スコープ外）

「アームの制御・動作計画の学習」の代替としては成立する。PLC を含む工場ライン全体の模擬は、そのままでは代替できない。

3.3 読み方のポイント

  • 利用者から見えているのは noVNC の画面と CLI だけ。その下で compose・ガードスクリプト・DDS・ros2_control・Gazebo 物理が動く。
  • 最大の安全装置は支援プロセス層にある（排他ガード、ros2-lab-net 非接続、restart なし、down-real.sh）。 ガードを通らない操作（docker compose --profile ... up の直叩き、docker compose down）が実機編の最大のリスク。
  • シミュと実機の差し替え点はハードウェア層の 1 箇所に閉じる、というのがこの構成の設計意図。実機側は未検証のため、README のチェックリストを消化するまで保証はない。
